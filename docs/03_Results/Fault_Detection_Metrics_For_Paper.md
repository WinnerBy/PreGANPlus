# 论文中故障检测指标的汇报说明

Stage3 阶段当前缺少统一的故障检测（P/R/F1）输出，难以在**部署/在线**层面计算各方法的故障检测性能。本文档说明：**是否可以用训练阶段的数据来描述故障检测**，以及如何在论文中规范表述。

---

## 1. 结论：可以，且需明确标注数据来源

**可以用训练阶段（编码器训练，Stage2）的故障检测指标来描述故障检测性能**，在机器学习论文中是常见且可接受的做法。前提是：

- 在论文中**明确写出**指标是在**哪个阶段、哪份数据**上得到的（例如“编码器训练集上的 P/R/F1”或“验证集”），**不要**让读者误以为是部署阶段（Stage3）的在线指标。

---

## 2. 当前流水线里故障检测指标从哪里来

- **训练阶段（Stage2）**：编码器训练时，`recovery/PreGANSrc/src/train.py` 中的 `accuracy()` 在每个 epoch 结束后，在**当前用于训练的那份数据**上计算异常检测的 TP/FP/FN，并得到 P、R、F1，通过 `tqdm.write(f'P = {p}, R = {r}, F1 = {f1}')` 输出。
- 因此，当前代码中的 P/R/F1 是在**编码器训练集**上计算的（与 `backprop` 使用的 `train_time_data` 等相同），**没有**单独的验证集划分。
- **部署阶段（Stage3）**：只有 PreGAN 的部分日志含有每步的 P/R/F1；其他方法及统一汇总目前缺失，因此难以在论文中写“Stage3 在线故障检测性能”。

因此，若要在论文中写故障检测性能，**可用的就是训练阶段这份数据上的 P/R/F1**。

### 2.1 方法论理由：为何用训练数据评估故障检测是合理的

从**统计与实验设计**角度，用训练阶段数据汇报故障检测性能是合理的：

- **推理阶段（Stage3）存在迁移干预**：在线仿真中，调度器会做出迁移决策，容器与负载的分布随之改变，用于故障检测的输入不再是“原始”观测序列，而是**经过迁移干预后的状态**。
- **数据规律会发生变化**：迁移会改变主机负载、响应时间等时序与空间分布，故障检测所依赖的数据规律（如时序模式、异常阈值对应的分布）在推理阶段与训练阶段**并不相同**，存在分布偏移（distribution shift）。
- **训练数据代表“基线”检测能力**：在训练所用故障标注数据上评估 P/R/F1，刻画的是编码器在**未受迁移干预影响的、可复现的故障模式**上的检测能力，即模型对故障本身的判别能力；推理阶段的指标则混入了“迁移带来的分布变化”，难以单独解释为“故障检测性能”。

因此，**用训练阶段数据描述故障检测**不仅是因为当前 Stage3 缺少统一输出，而且从方法论上也是合理的：训练数据上的指标更直接地反映“故障检测模型的能力”，而推理阶段的数据已掺杂迁移的因果/统计影响，二者语义不同。论文中可简要写出上述理由，以增强说服力。

---

## 3. 论文中建议的表述方式

### 3.1 推荐表述（明确数据来源）

在“实验/结果”部分描述故障检测时，建议采用类似表述（中英文可二选一或对应使用）：

- **中文示例**：  
  “故障检测性能（精确率 P、召回率 R、F1）在**编码器训练阶段**的故障标注数据上评估得到；由于当前部署阶段（Stage3）未统一输出在线检测指标，本文不报告部署阶段的 P/R/F1。”

- **英文示例**：  
  “Fault detection performance (Precision P, Recall R, F1-score) is **evaluated on the fault-labeled dataset used in the encoder training phase**. We do not report online (deployment-stage) P/R/F1, as the current Stage3 pipeline does not output these metrics for all methods.”

- **可选：加入方法论理由（中）**：  
  “此外，推理阶段存在迁移干预，用于故障检测的观测数据已非原始分布，其统计规律会随迁移决策发生变化；在训练数据上评估故障检测能力，更能直接反映编码器对故障模式的判别能力。”

- **可选：加入方法论理由（英）**：  
  “Moreover, during inference migrations intervene on the system, so the data used for fault detection is no longer from the original distribution—its statistical regularity changes with migration decisions. Evaluating fault detection on the training data thus more directly reflects the encoder’s discriminative capability on fault patterns.”

这样写即表明：**用的是训练阶段的数据**，没有混淆为“在线/部署”指标；若加入可选理由，可增强审稿人对“为何用训练数据”的认同。

### 3.2 若只汇报“训练集”指标时的注意点

- 当前 P/R/F1 是在**训练集**（与训练同源、同份数据）上算的，反映的是“模型在该故障标注数据上的检测能力”，**不是**独立验证集或测试集。
- 在论文中可写成“在编码器训练所用故障标注数据上的故障检测性能”或“on the encoder training set (fault-labeled data)”，避免给审稿人“在独立测试集上评估”的错觉。
- 若后续在 Stage2 中增加 **train/val 划分**，在**验证集**上汇报 P/R/F1 会更有说服力；届时可在论文中改为“在验证集上评估”（evaluated on the validation set）。

## 4. 与 Stage3 的关系

| 指标类型           | 数据来源           | 当前是否可用 | 论文中是否可写 |
|--------------------|--------------------|--------------|----------------|
| 训练阶段 P/R/F1   | 编码器训练用数据   | 是（train.py 每 epoch 输出） | **可以**，并注明“训练阶段/训练集” |
| 部署阶段 P/R/F1   | Stage3 在线仿真每步 | 仅 PreGAN 部分日志有，未统一 | 建议不写，或写明“仅 PreGAN 有、未统一” |

- **调度/能耗等系统指标**（nummigrations、energytotalinterval、slaviolations）：已在 Stage3 中完整采集，继续用 Stage3 汇总结果即可。
- **故障检测 P/R/F1**：用训练阶段数据是合理选择；只要在论文中写清“来自训练阶段/训练集”，就不会产生歧义。

---

## 5. 可选：训练阶段典型数值的获取方式

- 若需要写入论文的**具体数字**（如 F1）：可从 Stage2 训练日志中取**最后一个 epoch**（或你选定 epoch）的 `P = ..., R = ..., F1 = ...` 作为“编码器在该数据上的故障检测性能”。
- 代码中已有历史记录式注释（如 `constants.py` 中“Epoch 249 F1=0.8620”），说明此前实验中有类似数值可用；论文中可写“例如在训练结束时 F1 达到 …”并注明是训练集或验证集（若将来做了划分）。

---

## 6. 小结

- **可以用训练阶段的数据来描述故障检测**，并在论文中汇报 P/R/F1。
- **必须在论文中明确写出**：指标是在**编码器训练阶段**、在**训练所用故障标注数据**（或将来若有验证集则写“验证集”）上得到的，**不是**部署/在线阶段的指标。
- 按上述方式表述，在学术上是规范且可接受的；待 Stage3 支持统一输出在线 P/R/F1 后，可再补充“部署阶段故障检测性能”作为对比或未来工作。
