## 📊 论文中的故障定义

### 故障触发条件（基于ADE - Anomaly Detection Engine）

根据论文，故障需要**持续60秒**满足以下阈值条件：

| 故障类型 | 缩写 | 触发阈值/条件 | 物理含义 |
|---------|------|--------------|---------|
| **CPU 过载** | **CPUO** | CPU 利用率 > **90%** | 计算资源耗尽，任务处理延迟 |
| **异常内存分配** | **AMA** | RAM I/O 利用率 > **90%** | 内存带宽饱和，通常伴随 Swap 频繁 |
| **内存泄漏** | **MEL** | 内存分配速率 > **1MB/3s** | 应用程序存在 Bug，导致内存持续上涨 |
| **网络过载** | **NOL** | 网络缓冲区溢出 | 带宽不足或延迟过高导致数据堆积 |
| **异常磁盘利用** | **ADU** | 磁盘读写被节流 (Throttled) | I/O 操作超过硬件限制 |

### 故障标签分类

为了模型训练，上述5种物理现象被归纳为3类标签：
- **Class 1: CPU Fault** (源自 CPUO)
- **Class 2: Network Fault** (源自 NOL + ADU)
- **Class 3: RAM Fault** (源自 AMA + MEL)
- **Class 0: Normal** (无故障)

## 🔍 真实环境 vs 仿真环境差异

### 真实环境（Physical Testbed）

**机制**：
1. 调度器将高负载容器分配给节点
2. 容器运行消耗真实的CPU周期和内存页
3. 外部干扰（如NetLimiter）限制物理带宽
4. 检测：`docker stats`读取实时数据 → 超过阈值 → 标记为故障

**数据特征**：
- 数据充满噪声（Noise）
- 具有突发性尖峰（Spikes）
- 具有物理连锁反应（如内存满导致CPU颠簸）

### 仿真环境（Coupled-Simulation）

**机制**：
1. 调度器做出决策
2. **代理模型（Surrogate Model）**（通常是MLP/LSTM回归模型）接收当前状态+决策，预测下一时刻的CPU/RAM数值
3. 检测：将预测出的数值输入ADE逻辑 → 超过阈值 → 标记为故障

**数据特征**：
- 数据平滑（Smooth）
- 趋向于均值
- 缺乏极端值

**关键问题**：我们的代码中**没有ADE（异常检测引擎）**，而是使用统计方法（percentile、z-score等）来标记异常，这进一步加剧了问题。

## 🔍 根本问题分析

### 问题1：回归均值效应（Regression to the Mean）⚠️ **最关键**

**现象**：
- 神经网络回归模型（Surrogate）在训练时使用MSE（均方误差）作为损失函数
- 为了最小化整体误差，模型倾向于预测"平均值"

**后果**：
- 真实CPU：在40%和95%之间跳变
- 预测CPU：倾向于输出70%-85%之间的平滑曲线
- **判定失效**：由于阈值是硬性的90%，预测出的85%被判定为"正常"。**真正的故障被"平滑"掉了。**

**在我们的代码中**：
- 我们没有显式的Surrogate模型，但Simulator中的资源计算可能也存在类似的平滑效应
- 我们使用统计方法（percentile=90）来标记异常，但这种方法无法捕获真正的故障模式

### 问题2：缺乏时序累积效应

**现象**：
- 故障定义要求"持续60秒"
- 仿真模型可能偶尔预测出一个91%的点，但很难连续60个时间步都预测出>90%的值

**后果**：
- 只要中间有一个时间步预测回落到89%，故障计时器就会重置
- 导致故障漏报

**在我们的代码中**：
- 我们的时间窗口只有3（`n_window=3`），远小于60秒的要求
- 无法捕获持续性的故障模式

### 问题3：统计异常 ≠ 真正的故障

**现状**：
- 我们使用统计方法（percentile、z-score等）识别"异常"
- 这些"异常"只是资源使用的高峰，而非真正的故障
- 没有基于ADE的故障检测逻辑

**影响**：
- 模型学习到错误的模式
- 无法区分真正的故障和正常的高负载
- 精确度难以提升

## 🚀 提升方案（基于论文建议 + 实际环境借鉴）

### 方案1：概率性故障放大（Probabilistic Fault Amplification）⭐⭐⭐⭐⭐ **最推荐**

**来源**：论文策略B + 实际环境故障触发机制

**原理**（来自论文策略B）：
- 人为地"推"一把，模拟系统崩溃时的非线性特征
- 在"危险区"（如80%）以一定概率强制进入故障区（>90%）

**借鉴实际环境**：
- 实际环境中，故障是"负载诱发"的自然物理结果
- 当资源使用接近上限时，系统更容易发生故障
- 仿真环境可以模拟这种"接近上限时更容易故障"的特性

**实施步骤**：

1. **在资源计算后应用故障放大**（借鉴实际环境的故障触发机制）：
   ```python
   # 在 simulator/ 下创建 fault_amplification.py
   class FaultAmplifier:
       def amplify_fault(self, host_metrics, interval):
           """
           对接近阈值的资源使用进行故障放大
           host_metrics: {'cpu': 0.85, 'ram': 0.82, 'bw': 0.75}
           """
           # CPU过载放大
           if host_metrics['cpu'] > 0.80:
               # 以35%概率强制进入故障区（>90%）
               if random.random() < 0.35:
                   host_metrics['cpu'] = random.uniform(0.91, 0.99)
           
           # RAM过载放大
           if host_metrics['ram'] > 0.80:
               if random.random() < 0.35:
                   host_metrics['ram'] = random.uniform(0.91, 0.99)
           
           return host_metrics
   ```

2. **修改Simulator类**：
   ```python

   def simulationStep(self, decision):
       # 原有逻辑...
       
       # 故障放大（训练阶段）

               # 获取带宽使用率（需要添加相应方法）
               bw_usage = self.getBandwidthUsage(host)
               
               metrics = {'cpu': cpu, 'ram': ram_usage, 'bw': bw_usage}
               amplified = self.fault_amplifier.amplify_fault(metrics, self.interval)
               
               # 根据放大后的指标调整资源状态
               # （需要根据实际代码结构调整）
   ```

3. **基于ADE逻辑生成故障标签**：
   ```python
   # 在 recovery/PreGANSrc/src/utils.py 中
   def form_test_dataset_with_ade(data, host_metrics_history):
       """
       基于ADE逻辑生成故障标签，而不是统计异常
       需要持续60秒（或对应的时间步数）满足阈值
       """
       n_timesteps = data.shape[0]
       fault_labels = np.zeros(n_timesteps, dtype=bool)
       fault_types = np.zeros(n_timesteps, dtype=int)  # 0=正常, 1=CPU, 2=Network, 3=RAM
       
       # 故障持续时间计数器
       cpu_fault_duration = 0
       ram_fault_duration = 0
       network_fault_duration = 0
       
       # 阈值
       CPU_THRESHOLD = 0.90
       RAM_THRESHOLD = 0.90
       NETWORK_THRESHOLD = 0.90  # 需要根据实际情况调整
       FAULT_DURATION = 60  # 60秒，需要转换为时间步数
       
       for i in range(n_timesteps):
           # 检查CPU过载
           if host_metrics_history[i]['cpu'] > CPU_THRESHOLD:
               cpu_fault_duration += 1
               if cpu_fault_duration >= FAULT_DURATION:
                   fault_labels[i] = True
                   fault_types[i] = 1  # CPU Fault
           else:
               cpu_fault_duration = 0
           
           # 检查RAM过载
           if host_metrics_history[i]['ram'] > RAM_THRESHOLD:
               ram_fault_duration += 1
               if ram_fault_duration >= FAULT_DURATION:
                   fault_labels[i] = True
                   fault_types[i] = 3  # RAM Fault
           else:
               ram_fault_duration = 0
           
           # 检查网络过载
           if host_metrics_history[i]['bw'] > NETWORK_THRESHOLD:
               network_fault_duration += 1
               if network_fault_duration >= FAULT_DURATION:
                   fault_labels[i] = True
                   fault_types[i] = 2  # Network Fault
           else:
               network_fault_duration = 0
       
       return fault_labels, fault_types
   ```

- 精确度：16.0% → **50-70%** ⭐⭐⭐⭐⭐
- 召回率：75.9% → 70-85%
- F1分数：26.4% → 60-75%

**实施难度**：中等（论文推荐，成本最低）

### 方案2：基于残差的噪声注入（Residual-based Noise Injection）⭐⭐⭐⭐

**来源**：论文策略A + 实际环境数据特性

**借鉴实际环境**：
- 实际环境的数据充满噪声，具有突发性尖峰
- 仿真环境的数据过于平滑，缺乏波动
- 添加符合真实数据分布的噪声，模拟实际环境的波动

**原理**（来自论文策略A）：
- 不要直接信任Surrogate模型的原始输出，需叠加符合真实数据分布的噪声
- 负载越高，波动越大

**实施步骤**（借鉴实际环境的噪声特性）：

```python
# 在 simulator/host/Host.py 中
def getCPU(self):
    ips = self.getApparentIPS()
    cpu_base = 100 * (ips / self.ipsCap)
    
    # 添加噪声（借鉴实际环境的波动特性）
    if self.env.training:  # 仅在训练阶段添加噪声
        # 动态噪声：负载越高，波动越大（与实际环境一致）
        noise_std = cpu_base * 0.10  # 10%的波动
        noise = np.random.normal(0, noise_std)
        cpu_noisy = np.clip(cpu_base + noise, 0, 100)
        return cpu_noisy
    
    return cpu_base

# 或者使用通用方法
def add_noise_to_metrics(self, base_metrics):
    """
    对基础指标添加噪声，模拟真实环境的波动
    """
    noisy_metrics = {}
    
    for key, value in base_metrics.items():
        # 动态噪声：负载越高，波动越大
        sigma = value * 0.15  # 15%的波动
        noise = np.random.normal(0, sigma)
        
        # 叠加噪声并截断
        noisy_metrics[key] = np.clip(value + noise, 0.0, 1.0)
    
    return noisy_metrics
```

**预期效果**：
- 精确度：16.0% → **40-60%**

**实施难度**：简单

### 方案3：实现基于阈值的故障检测（借鉴ADE逻辑）⭐⭐⭐⭐⭐ **最推荐**

**来源**：论文ADE定义 + 实际环境故障检测需求

**借鉴实际环境**：
- 虽然实际环境代码中没有显式实现ADE，但论文中定义了明确的故障阈值
- 仿真环境可以使用相同的阈值逻辑
- 基于90%阈值 + 持续60秒的故障检测

**原理**：
- 在Simulator中实现故障检测逻辑
- 基于90%阈值检测CPU、RAM、Network过载
- 检查持续60秒的故障持续时间
- 在标签生成时使用故障信息，替代统计方法

**实施步骤**：

1. **在Simulator中实现故障检测逻辑**：
   ```python
   # 在 simulator/Simulator.py 中添加
   class Simulator():
       def __init__(self, ...):
           # ...
           self.fault_history = {}  # 记录每个主机的故障持续时间
           self.fault_thresholds = {
               'cpu': 90.0,  # CPU过载阈值
               'ram': 90.0,  # RAM过载阈值（使用率）
           }
           self.fault_duration_required = 60  # 持续60秒
       
       def detect_faults(self):
           """检测当前interval的故障状态"""
           faults = {}
           for host in self.hostlist:
               host_id = host.id
               cpu = host.getCPU()
               ram_usage = host.getCurrentRAM()[0] / host.ramCap.size * 100
               
               # 检查CPU过载（持续60秒）
               if cpu > self.fault_thresholds['cpu']:
                   if host_id not in self.fault_history:
                       self.fault_history[host_id] = {'cpu': 0, 'ram': 0}
                   self.fault_history[host_id]['cpu'] += self.intervaltime
               else:
                   if host_id in self.fault_history:
                       self.fault_history[host_id]['cpu'] = 0
               
               # 检查RAM过载（持续60秒）
               if ram_usage > self.fault_thresholds['ram']:
                   if host_id not in self.fault_history:
                       self.fault_history[host_id] = {'cpu': 0, 'ram': 0}
                   self.fault_history[host_id]['ram'] += self.intervaltime
               else:
                   if host_id in self.fault_history:
                       self.fault_history[host_id]['ram'] = 0
               
               # 判断是否发生故障（持续60秒）
               if host_id in self.fault_history:
                   if self.fault_history[host_id]['cpu'] >= self.fault_duration_required:
                       faults[host_id] = 'cpu'
                   elif self.fault_history[host_id]['ram'] >= self.fault_duration_required:
                       faults[host_id] = 'ram'
           
           return faults
   ```

2. **在数据收集时记录故障状态**：
   ```python
   # 在 stats/Stats.py 中
   def saveHostInfo(self):
       # ... 原有逻辑 ...
       
       # 检测故障（借鉴实际环境的故障检测逻辑）
       if hasattr(self.env, 'detect_faults'):
           faults = self.env.detect_faults()
           hostinfo['faults'] = faults
   ```

3. **在标签生成时使用故障信息**：
   ```python
   # 在 recovery/PreGANSrc/src/utils.py 中
   def form_test_dataset_with_faults(data, fault_history):
       """
       基于故障历史生成标签，而不是统计异常
       借鉴实际环境的故障定义
       """
       n_timesteps = data.shape[0]
       fault_labels = np.zeros(n_timesteps, dtype=bool)
       
       for i in range(n_timesteps):
           if i in fault_history:
               # 如果该时间步有故障，标记为异常
               if len(fault_history[i]) > 0:  # 至少有一个主机故障
                   fault_labels[i] = True
       
       return fault_labels
   ```

**预期效果**：
- 精确度：16.0% → **50-70%** ⭐⭐⭐⭐⭐
- 使用与论文一致的故障定义

**实施难度**：中等

### 方案5：调整Surrogate模型的损失函数

**来源**：论文策略D

**原理**（来自论文策略D）：
- 如果必须重新训练Surrogate模型，不要只用MSE
- 对高负载样本（Label > 0.8）赋予更高的权重

**实施步骤**：

```python
# 加权损失函数
def weighted_mse_loss(y_true, y_pred):
    weights = torch.where(y_true > 0.9, 10.0, 1.0)
    loss = torch.mean((y_true - y_pred) ** 2 * weights)
    return loss
```

**预期效果**：
- 精确度：16.0% → **30-50%**

**实施难度**：中等（需要重新训练Surrogate模型，但我们可能没有显式的Surrogate模型）

## 💡 关键洞察

1. **论文的核心发现**：
   - 仿真环境过于理想化，数据过于平滑
   - 回归均值效应导致无法触发90%阈值
   - 概率性故障放大是最低成本且最有效的方法

2. **我们的代码现状**：
   - 没有ADE（异常检测引擎）
   - 使用统计方法标记异常，而非基于阈值的故障检测
   - 时间窗口太小（3 vs 60秒要求）

3. **改进方向**：
   - 实施概率性故障放大（论文推荐）
   - 实现基于ADE逻辑的故障检测
   - 改进FPE模型以支持更长的时序模式

4. **组合方案效果最好**：
   - 概率性故障放大 + ADE逻辑 + 模型改进
   - 预期精确度可以超过50%，甚至达到70-80%
