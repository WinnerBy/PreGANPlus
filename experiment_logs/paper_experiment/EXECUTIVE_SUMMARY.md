## V. 问题诊断与解决方案

### 问题1：PreGANPlus的响应时间恶化

**症状：**
```
响应时间：150.8ms → 229.3ms (+52%)
虽然能耗改进了1.1%，但这远远不值得
```

**根本原因假设：**
1. GAN训练1200步（vs PreGAN 300步）可能过度拟合能耗目标
2. GAN的损失函数可能权重不平衡
3. 调度矩阵生成时过度优化了能耗，忽视了响应延迟

**诊断步骤：**
```
1. 检查 scripts/paper_experiment_stage3_gan_training.py
   ├─ 确认GAN损失函数中的权重配置
   ├─ 查看 (1-λ)*disc_loss + λ*gen_loss 中的λ值
   └─ 如果λ过高，会过度优化能耗

2. 检查 recovery/PreGANPlus.py
   ├─ run_model() 中的权重平衡
   ├─ GAN生成的调度矩阵是否合理
   └─ 是否存在约束条件被忽视

3. 对比PreGAN vs PreGANPlus的实际调度决策
   └─ 通过日志分析，看PreGANPlus是否做了不同的选择
```

**修复方案（优先级）：**
```
方案A（推荐，快速）：
├─ 将PreGANPlus的GAN训练步数降回300（与PreGAN一致）
├─ 重新运行阶段3和阶段4
└─ 预期：响应时间恢复，保持能耗改进

方案B（彻底）：
├─ 重新调整GAN损失函数权重
├─ 在能耗和响应时间之间找到更好的平衡点
├─ 测试多个权重组合（α=0.3, 0.5, 0.7）
└─ 预期：可能实现比PreGAN更好的整体性能

方案C（不推荐）：
└─ 保持现状，将PreGANPlus标记为"能耗优化专项"
   （论文可能显得方法设计有缺陷）
```

**预期结果：**
```
方案A结果（预期）：
├─ 响应时间：229.3ms → ~155ms (接近PreGAN)
├─ 能耗：维持 1,973 KJ (保持改进)
├─ 评价：恢复可用性 ✓

方案B结果（最优期望）：
├─ 响应时间：~145ms (比PreGAN更好)
├─ 能耗：~1,980 KJ (保持改进)
├─ 评价：成为第二代的真正改进 ✓✓
```

### 问题2：DFTM的响应时间异常

**症状：**
```
响应时间：-443,636 ms (负数，物理上不可能)
```

**原因：**
- 日志记录错误，或
- 响应时间计算时出现数据溢出/bug

**修复步骤：**
```
1. 检查 recovery/DFTM.py
   ├─ run_model() 中的响应时间计算
   ├─ 是否使用了错误的符号或单位转换
   └─ 是否存在时间戳倒序的情况

2. 查看 main.py 中的统计收集
   └─ stats.saveStats() 对响应时间的累加方式

3. 重新运行阶段4测试
   └─ 比较日志中的逐步数据
```

**临时方案：** 
```
在论文中排除DFTM的数据，或标注为"实现有bug"
不应该以异常数据来对比其他方法
```

---

### 问题3：PCFT的迁移爆炸

**症状：**
```
迁移数：907次（vs基准176次，增加414%！）
单次迁移时间：161.55ms（vs基准11.11ms，增加1450%！）
```

**根本原因：**
- PCFT（预防性容错）设计为激进的故障预测
- 频繁预测故障并主动迁移（过度激进）
- 这导致大量不必要的容器迁移

**论文建议：**
```
❌ 不将PCFT作为主要对标方法
✓ 可以在"局限性"章节讨论，说明：
  "传统预防性方法（PCFT）虽然目的是提高容错能力，
   但会导致过度的容器迁移（907次 vs 176次），
   造成显著的资源开销，这与我们的预测性优化思路相反"
```
